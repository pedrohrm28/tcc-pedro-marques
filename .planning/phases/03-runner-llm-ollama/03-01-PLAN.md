<data_facts>
<!-- FATOS já verificados no CONTEXT.md (D-01..D-08). NÃO re-investigar; apenas codificar e testar. -->

- Ollama API em `http://localhost:11434`. Endpoint `/api/generate` (POST). `requests` JÁ está em
  requirements.txt — usar `requests` (não adicionar o pacote `ollama`).
- Corpo da chamada (D-03/D-05/D-07): JSON com
  `{"model": <modelo>, "prompt": <texto>, "stream": false, "format": "json",
    "keep_alive": -1, "options": {"temperature": 0, "seed": 42}}`.
  Opcional: `options.num_predict` (teto de tokens) — pode ajudar a evitar respostas longas.
- Resposta de /api/generate (stream=false): JSON com campo `"response"` (string) e métricas
  `"eval_count"`, `"eval_duration"` (ns), `"load_duration"` (ns), `"total_duration"` (ns) (D-08).
  tok/s = eval_count / (eval_duration / 1e9).
- D-03: o LLM recebe a lista de tokens JÁ tokenizada (vinda do loader) e devolve um **array JSON de
  tags**, uma por token, na MESMA ordem. O LLM NÃO re-tokeniza. `format="json"` força saída JSON.
  O `response` do Ollama com `format=json` vem como STRING JSON — fazer `json.loads(response)` para
  obter o array (pode vir como `{"tags": [...]}` ou `[...]` dependendo do prompt — o parser deve
  aceitar ambos: se for dict, extrair a primeira lista de valores).
- D-04 (fallback rastreável): fallback de NER = "O"; fallback de UPOS = "NOUN". O parser aplica
  fallback token-a-token quando: (a) `json.loads` falha; (b) o array tem comprimento != nº de tokens;
  (c) uma tag individual está fora do esquema (UPOS: não ∈ UPOS_VALIDOS). Cada token consertado conta
  como 1 fallback. NUNCA retornar lista de tamanho diferente do nº de tokens.
- D-03 esquema por tarefa: NER = tags IOB (strings livres no formato "O" / "B-xxx" / "I-xxx"; a
  validação por-tag de NER é leve — aceitar "O" e qualquer "B-"/"I-" prefixado; tags vazias/None
  caem em fallback "O"). UPOS = tag ∈ UPOS_VALIDOS, senão fallback "NOUN".
</data_facts>
